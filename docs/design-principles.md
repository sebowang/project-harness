# 设计原则

## 1. Harness 是工程环境，不是文档集合

Project Harness 的目标是让 Agent 能可靠地理解项目、控制变更范围并提供验证证据。文件存在本身没有价值；只有当规则能被发现、事实能被定位、检查能被执行时，Harness 才成立。

## 2. 不同信息使用不同载体

| 信息类型 | 推荐载体 | 原因 |
|---|---|---|
| 仓库长期规则 | `AGENTS.md` | Agent 自动发现，适合简短且稳定的约束 |
| 当前架构事实 | `docs/project-map.md` | 可由源码复核，允许随实现更新 |
| 长期决策与不变量 | `docs/decisions/` | 保留背景、取舍、后果和替代关系 |
| 产品需求 | `docs/prd/` | 与架构事实和技术决策分离 |
| 外部接口与依赖事实 | `docs/reference/` | 记录观察结果，不暗示已批准决策 |
| 重复工作流程 | `docs/workflows/` | 工具中立的流程事实源，可由不同 Agent 入口复用 |
| 工具自动发现入口 | `.agents/skills/`、`.claude/skills/` | 只负责路由，不复制完整流程 |
| 可重复验收 | `tests/harness/` | 用退出码和可观察结果提供证据 |
| 跨会话临时状态 | 单一 handoff 文件 | 仅在确有恢复需求时创建，避免多份状态冲突 |

## 3. 默认不生成多套状态文件

任务状态、会话状态、进度、命令历史和日志如果同时维护，很容易互相矛盾，也会持续占用 Agent 上下文。基础初始化不创建这些文件。长任务需要交接时，只维护一个包含目标、进度、验证、风险和下一步的 handoff 文件。

## 4. 初始化分为脚手架与勘察

脚本可以可靠完成目录、模板、配置和检查入口的创建，但不能可靠推断业务边界、实际入口、共享契约或可运行命令。因此初始化必须分两步：

1. 脚手架初始化：非破坏性地安装最小基线。
2. 仓库勘察：阅读源码和现有配置，填写项目地图与真实验证命令，再由研发确认。

## 5. 完成必须有分层证据

`scripts/check-harness.ps1` 只能证明 Harness 文件和配置可被读取。它不能证明业务代码正确。项目完成条件应至少区分：

- Harness 完整性
- 构建
- 单元/集成测试
- Lint/类型检查
- 手工或自动 Smoke Check
- 未执行检查及其风险

Harness 安装状态与项目就绪状态必须分开：结构检查通过只表示 `installed`。项目事实占位符已清除，并且所需项目验证已配置或存在明确豁免后，才能报告 `ready` 或 `ready with waiver`。

## 6. 安全边界必须机械生效

通用脚本无法阻止 Agent 绕过它直接执行命令，因此本项目不提供“安全命令守卫”并声称其能够拦截风险操作。生产项目应按风险使用真实权限、Sandbox、审批、Hook、CI 保护、数据库隔离和发布环境控制。

## 7. 文档漂移需要项目化规则

“文档是否过期”无法通过通用脚本完全判断。`check-doc-drift.ps1` 提供可配置的文本断言与模板占位符检查；每个项目仍需把高价值事实转化为自己的漂移规则或 Harness。
