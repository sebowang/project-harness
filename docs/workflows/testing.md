# Testing

## 目标

为当前变更选择风险相称、可复现的验证证据，不把 Harness 完整性检查误报为业务测试通过。

## 步骤

1. 从 `docs/verification.md`、变更范围和已有 CI 找到最小有效检查。
2. 区分 Harness、构建、测试、Lint/类型检查和手工 Smoke Check，并说明各自证明的边界。
3. 先运行最快且最能定位问题的检查，再运行受影响的完整检查。
4. 失败时保留命令、退出码和必要输出；不得用未验证的替代命令掩盖失败。
5. 报告实际运行的命令、结果、未运行检查及其风险。

## 验证强度

按变更的实际影响选择最低验证强度；项目的 `docs/verification.md` 或 CI 规定更严格要求时，以更严格者为准。

| 影响边界 | 最低验证证据 |
|---|---|
| 仅改不影响行为的说明文字或格式 | 复核变更内容；修改 Harness 文件时运行 Harness 检查 |
| 内部实现，未改变共享契约 | 受影响单元/模块测试，以及适用的 Lint 或类型检查 |
| 公共接口、数据模型、配置 schema、依赖或跨模块契约 | 受影响的契约/集成测试和构建；项目验证矩阵要求全量套件时运行全量套件 |
| 数据库迁移、权限、部署、支付或生产数据 | 前述适用检查，加上已获批准的隔离环境验证、dry-run/preview、回滚或人工确认；不得默认执行生产操作 |

无法满足对应强度时，报告必须列出缺口、原因、风险和下一步；不得把较低强度检查写成“验证通过”。

新增或修改外部接口请求构造或响应解析、字段映射、共享契约，或仅靠代码审查难以确认的可独立验证逻辑时，必须新增或引用覆盖该行为的自动化测试。优先更新已有单元或集成测试；没有合适入口时，按 `harness-authoring` 新增 Harness。无法自动化时，交付说明必须记录原因、替代验证、遗留风险和下一步，并优先评估最小的可测边界调整。

## 新增测试的价值筛查

新增自动化测试前或审查时，确认它能回答以下问题：

1. 它保护的具体行为或契约是什么，哪一种合理回归会让它失败？
2. 它断言的是可观察结果、状态或边界，而非偶然的私有实现路径吗？
3. 相比已有测试，它新增了哪一种失败模式或风险覆盖？没有新增时，优先合并或增强已有测试。

不能回答这些问题的检查可以作为临时调试手段，但不应仅为数量、目录或覆盖率而保留为长期回归测试。不要用通用 diff 规则猜测“改动必须新增测试”；由变更风险、项目测试策略和代码审查共同判断。
