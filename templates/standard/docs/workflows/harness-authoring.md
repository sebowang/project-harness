# Harness Authoring

## 使用条件

- 新增或修改外部接口请求构造或响应解析、字段映射、共享契约，或仅靠代码审查难以确认的可独立验证逻辑，而项目现有自动化测试没有覆盖该行为。
- 回归已经发生或很可能重复发生，且检查可以在不启动完整产品的情况下运行。

命中上述任一条件时，必须先更新已有自动化测试；没有合适入口时，新增 Harness。Harness 是一种外部回归检查，不替代项目已有的单元或集成测试。

## 步骤

1. 定义一个可观察契约、明确失败信号，以及它防止的具体回归。
2. 复用项目已经验证的测试或运行工具。
3. fixture 使用合成、确定性数据，并与生产隔离。
4. 全部断言通过时才返回退出码 `0`。
5. 记录命令、前置条件、输入、输出、覆盖范围及相对已有测试新增的失败模式。
6. 需要统一执行时，把命令加入 `harness.config.json`。

涉及第三方依赖、遗留运行时或特定编译器时，先从项目现有构建、测试、依赖清单和 Reference 中勘察可复用配方；未验证的命令不得臆造。首次得到可重复执行的配方后，把实际前置条件、版本和命令记录到项目的 `docs/reference/` 或 `docs/lessons/`，不把项目专属工具链写成通用 Harness 假设。

不为满足目录结构、测试数量或覆盖率而创建 Harness。优先断言可观察结果，不把偶然的私有调用路径当作契约；若已有测试已覆盖同一风险，优先增强或复用它。无法自动化时，在交付说明记录原因、替代验证、遗留风险和下一步，并优先评估最小的可测边界调整。
