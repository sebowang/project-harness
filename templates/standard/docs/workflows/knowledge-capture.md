# Knowledge Capture

## 目标

把用户纠正、重复故障和实施经验放到唯一合适的项目载体中，避免聊天记录成为唯一事实源，也避免把所有内容堆进 `AGENTS.md` 或 Skill。

## 触发与边界

- 用户可以明确要求“检查当前或最近可访问的会话是否有值得沉淀的内容”“把这个决定记录下来”或“判断这套流程是否适合固化为 Skill”。
- 检查范围（`accessible-context`）只包括当前 Agent 实际可读取的对话上下文和仓库证据。执行前必须说明范围；无法访问的历史任务不得凭印象补写。
- 仅发现模式（`discovery-only`）：用户只要求“检查、发现、列候选”时，输出候选及建议位置，不修改文件。用户明确要求“记录、沉淀、更新”时，完成分类后写入；目标或分类仍会显著影响结果时先展示建议并确认。
- Agent 发现重复纠正、重复失败、共享契约或长期不变量等强信号时，可以主动提示候选，但默认不自动创建长期规则、Decision Record 或 Skill。
- 不根据单个关键词机械分类。用户要求“固化成 Skill”也必须通过 Skill 晋级门槛；不成熟时说明原因，并建议保留为 Lesson 或工作流候选。

## 分类路由

| 内容 | 记录位置 | 判断标准 |
|---|---|---|
| 必须长期遵守的稳定规则 | `AGENTS.md` | 违反后会改变团队协作边界或安全要求 |
| 用户可见目标、范围和验收条件 | `docs/prd/` | 产品行为或用户任务发生变化 |
| 有取舍的长期选择和不变量 | `docs/decisions/` | 使用统一 Decision Record；系统红线用 `System Invariant`，技术选择用 `Architecture Decision` |
| 已从源码、接口或环境验证的当前事实 | `docs/project-map.md` 或 `docs/reference/` | 描述“现在是什么”，不授权改变它 |
| 可复用的失败教训、用户纠正和操作陷阱 | `docs/lessons/` | 未来任务可能重复踩到，且不属于规则、事实或决策 |
| 已稳定复用的执行流程 | `docs/workflows/` 和对应 Skill | 至少两次独立成功复用，输入、输出和验证方式清楚 |
| 仅当前任务有效的进度、阻塞和下一步 | `docs/active-plan.md` 或 `docs/handoff.md` | 任务完成后不应继续作为长期知识 |
| 未确认猜测、临时排障记录 | 项目已有的 `notes/` 或其他临时目录 | 尚未被证实或不值得长期维护 |

## 步骤

1. 声明本次实际检查的会话、文件和证据范围。
2. 先列出候选、证据、建议类型、目标路径和不沉淀风险，不把推测写成结论。
3. 选择一个主记录位置；不要把同一段正文复制到多个目录。
4. 如果经验改变了规则、需求、决策或事实，同时更新对应主文档，并在 Lesson 中只保留经验来源和迁移结果。
5. 如果只是临时 workaround、一次性日志或未确认假说，留在项目既有临时目录，不升级为长期文档。
6. 报告实际写入内容；只做候选发现时，明确说明未修改文件。

## Skill 晋级门槛

不要为一次性知识创建 Skill。只有在流程至少两次独立成功复用，并且能够说明输入、步骤、失败信号、验证方式和不适用范围时，才将它整理为 Skill；Skill 只描述流程，不复制项目事实。

## 项目目录边界

`code/`、`src/`、`assets/`、`notes/` 等源码、素材和临时记录目录由目标项目自行决定。Harness 不创建、移动或重命名这些目录；首次勘察时只记录真实布局和责任边界。
